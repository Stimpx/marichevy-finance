# Выпуск v95-rc1: сервер, данные и GitHub Pages

Статус: подготовка, **не разрешение на публикацию**. Этот документ не выполняет
команды автоматически. Рабочая база, её схема и права пока не изменяются.

Подтверждённый адрес — `https://finance.marichev.pro`. GitHub Pages использует
`main:/` и системный workflow `pages-build-deployment`. Последняя успешная
сборка/развёртывание и публичный HTML соответствуют `bfc7ce5` (v94).
Слияние в main запускает публикацию, поэтому оно является частью выпуска.

## До итогового разрешения

1. Зафиксировать полный commit кандидата, SHA-256 `index.html` и всех трёх SQL:
   `001_family_state_cas.sql`, `002_restrict_table_capabilities.sql`,
   `003_bound_membership_lookup.sql`. Сверить их с результатами проверок.
2. На изолированном Supabase проверить те же членство, RLS, внешние ключи и
   hardening на двух вымышленных семьях. Повторить прямой PostgREST и сценарии
   текущего клиента после изменения серверной модели. Реальные данные на стенд
   не переносить. Сохранённые результаты старой fixture v1 не подменяют эту проверку.
3. Согласовать форму на настоящих устройствах: Safari/iPhone и Яндекс Browser/ПК.
   Проверить четыре основных поля, «Детали», ввод `1 250,50`, клавиатуру и Save.
   До выпуска использовать только вымышленные данные в согласованном предпросмотре.
4. Сохранить локальный JSON с каждого устройства отдельно, исходные pending,
   primary и копии восстановления, а также отдельный согласованный серверный
   резерв. Одинаковое имя файла не означает одинаковое содержимое. Экспорты
   держать закрыто, без репозитория, демо и тестового Supabase.
5. В закрытой среде восстановить резерв и сравнить все коллекции, ID, неизвестные
   JSON-поля, tombstones, связи, периоды и суммы в копейках. Проверить, что ни одна
   локальная очередь не потеряна и неоднозначные варианты согласованы.
6. Зафиксировать всех серверных writers. Встроенные CAS/legacy пути проверены,
   внешние функции/задания должны подтвердить совместимость; каталог БД сам по
   себе не доказывает отсутствие внешних клиентов. Новая функция членства
   сохраняет service_role lookup, а пользовательский lookup привязывает к auth.uid().
7. Получить одно итоговое разрешение владельца на конкретные commit/SQL/домен,
   описанные результаты и приведённый ниже возврат. Пока хотя бы один пункт открыт,
   кандидат не объявляется готовым к публикации.

## Согласованный порядок установки после разрешения

1. Остановить изменения на обоих устройствах и прочих writers; сохранить свежие
   закрытые копии. Записать текущие household/revision без вывода истории в логи.
2. Повторить read-only проверку схемы и preflight. При изменении колонок, функций,
   политик, владельцев, триггеров или grants остановиться и проверить расхождение.
3. Применить 001, затем 002 и 003. 001 начинает с протокола 1, не заменяет JSON и
   не активирует новую синхронизацию. 002 снимает TRUNCATE/TRIGGER с клиентских
   ролей. 003 ограничивает lookup членства. Сверить JSON и внешние ключи с резервом.
   Ни staging_fixture, ни staging_membership_v2 в рабочую базу не применять.
4. Активировать протокол 2 только согласованной семьи при совпадении ожидаемой
   revision. `server/activate_household.sql` — шаблон для psql, не готовое тело
   Management API запроса. Guard нельзя обходить при несовпадении revision.
5. Опубликовать ровно проверенный frontend commit через существующий main/Pages.
   Между активацией и обновлением HTML старые writers должны оставаться остановлены:
   сервер отклоняет их legacy-запись. Не запускать отдельную публикацию HTML заранее.
6. Дождаться успешного Pages deployment именно выбранного commit, проверить HTTPS,
   CNAME и SHA публичного HTML. На обоих устройствах загрузить новую версию.
7. Проверить вход, неизменённую историю и разрешённую владельцем настоящую правку
   с появлением на втором устройстве после reload. Фиктивные расходы в рабочую
   историю не вносить. Убедиться, что очереди подтверждены сервером, затем снять паузу.

## Условия остановки и возврат

Остановить writers при неверном SHA, отказе входа/изоляции, изменении истории,
потере pending, несовпадении CAS/revision или неуспешном Pages deployment.
Сначала сохранить новые серверные и локальные варианты, затем выбирать возврат.

Прежняя статика сохранена из опубликованного `bfc7ce5` в закрытом
`pre-release-static-bfc7ce5-PRIVATE.zip`. Её можно вернуть новым коммитом в main
и дождаться Pages. Это **не** возврат базы и **не** резерв истории. При оставшемся
протоколе 2 v94 не сможет отправлять legacy-запись; до решения проблемы изменения
на устройствах должны оставаться остановлены.

Возврат 2→1 — отдельный контролируемый шаг `server/rollback_household.sql`:
остановить writers, сохранить новые данные/очереди, сверить текущую revision и
подтвердить снятие CAS. Сам rollback меняет только протокол и серверную revision,
не JSON. Новые колонки/RLS и устранение лишних прав не удалять ради возврата HTML.
Старый дамп нельзя накатывать поверх новых операций. Восстановление истории из
резерва требует отдельного сопоставления новых операций и согласования владельца.

Если серверную миграцию не удалось применить до активации/публикации, оставить
v94 и остановить выпуск. Успешный локальный тест или наличие ZIP не заменяют
проверенного рабочего резерва, hosted проверки и разрешения на публикацию.
