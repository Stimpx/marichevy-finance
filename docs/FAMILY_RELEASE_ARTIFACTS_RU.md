# Отдельные файлы семейного выпуска v95

Сначала принимается вымышленное демо, затем отдельно выпускается действующий
семейный банк. Публичные аккаунты и FREE — следующий проектный этап. Создание
этих архивов ничего не публикует, не запускает SQL и не изменяет семейную историю.

## Два пакета с разным назначением

`tools/build_family_release.py` читает только явно перечисленные файлы checkout
и создаёт четыре файла в частной папке **вне репозитория**:

| Файл | Назначение |
| --- | --- |
| `family-static.zip` | Только шесть файлов сайта: `index.html`, `favicon.svg`, `favicon.ico`, `favicon-32.png`, `apple-touch-icon.png`, `CNAME`. |
| `family-static.MANIFEST.json` | Внешний список SHA-256 этих шести файлов, SHA/размер ZIP, Git HEAD и признак незакоммиченных изменений. Внутри статического ZIP нет manifest или других дополнительных файлов. |
| `family-operator.zip` | Только SQL 001–003, шаблоны активации/возврата и перечисленные ниже инструкции для сопровождающего. На сайт этот пакет не выкладывают. |
| `family-operator.MANIFEST.json` | Внешний список SHA-256 операторских файлов и ZIP, с той же идентификацией исходного кандидата. |

Операторские инструкции: `RELEASE_RUNBOOK.md`, `PRIVATE_RESTORE_ACCEPTANCE.md`,
`DEVICE_QUEUE_CAPTURE_MAC_RU.md`, `LOCAL_QUEUE_BACKUP_RU.md`, `SYNC_SERVER.md`,
`PRODUCTION_SCHEMA_FINDINGS.md` и этот документ, все из `docs/`.
Точный список закреплён в `OPERATOR_FILES` и проверяется тестом.

Ни один пакет не включает `public/`, account gateway, SQL 004, отдельную
регистрацию публичных аккаунтов, FREE-документы, `preview/`, демо, `.env`, Git,
серверные или устройственные резервные файлы, сессии и экспорты Auth.
Корневой HTML сохраняется **без преобразования**: его прежний семейный вход,
конфигурация подключения, имена и встроенный график не обезличиваются.
Поэтому оба пакета и manifests до выпуска остаются частными. Это не замена
серверного резерва или исходных очередей телефона и ПК.

## Как получить проверяемый кандидат

Сопровождающий сначала завершает изменения и проверки, затем фиксирует исходники
коммитом. Из корня checkout:

```sh
python3 tools/build_family_release.py --output-dir /workspace/private-family-release-candidate
```

Если нужно сохранить предыдущую сборку, используйте **новую** частную папку
с другим именем. Родительская папка должна существовать. Сборщик сам создаёт
выходную папку с доступом `0700`, файлы — `0600`; уже существующая папка должна
принадлежать текущему пользователю и иметь ровно такие права. Это ограничение
доступа, а не шифрование. Новые образы worker с частными данными не публикуются.

Сборка из изменённого checkout допустима для локальной проверки, но честно
содержит `git_dirty: true`. Она не является зафиксированным итоговым кандидатом.
Последняя сборка после коммита должна иметь `git_dirty: false`, ожидаемый полный
Git HEAD и SHA текущего `index.html`. Не редактируйте manifests ради этого статуса.

Проверка Git намеренно консервативна: сравниваются HEAD/index, наличие новых
файлов, метаданные отслеживаемых файлов и уже прочитанные байты выбранных
исходников. Изменённые метаданные другого файла считаются `dirty`, даже если его
содержимое могло остаться прежним. Сборщик не открывает его ради уточнения.
Обычный `git status` и исполняемые Git-фильтры не запускаются; пользовательские
настройки Git и переменные с credentials не наследуются. Поэтому `dirty: true`
может означать неопределённость, а не доказанную правку содержимого.

Сборщик читает содержимое каждого исходника один раз. Изменение Git или исходного
файла во время сборки вызывает отказ. Оба manifests содержат общий
`source_snapshot_sha256` для списка хешей всех выбранных исходников; отдельный
`files` описывает точный состав соответствующего ZIP. Перед передачей и установкой
сравните полный состав, SHA-256 файлов после распаковки и SHA-256 самого ZIP.
`index_sha256` должен совпадать с проверками интерфейса/денежных расчётов.
Хеши доказывают совпадение файлов, а не готовность сервера или устройств.

Порядок ZIP, время и права его участников фиксированы. При тех же исходниках,
HEAD и состоянии checkout повторный запуск даёт те же четыре файла. В уже
непустой выходной папке разрешён только побайтно одинаковый результат. Лишний
файл, неполный комплект или предыдущая другая сборка вызывает отказ без замены
существующих файлов. Symlink во входных/выходных путях не допускается.
Сборщик не ищет резервные папки, не читает переменные среды/ключи и не обращается
к сети, браузеру, Supabase или истории настоящей семьи.

## Установка и возврат — отдельное решение

Сборка не создаёт веток, не меняет `main` и не загружает артефакты на Pages.
Для семейного выпуска нужен отдельный проверяемый release-коммит с шестью
статическими файлами, а не автоматическое слияние всех разрабатываемых функций
PR5. SQL из операторского пакета проверяется и применяется отдельно по
[RELEASE_RUNBOOK.md](RELEASE_RUNBOOK.md), после свежего частного резерва,
проверки очередей устройств и единого итогового разрешения владельца.

Возврат прежнего HTML, изменение протокола и восстановление данных — разные
операции. Старый серверный снимок нельзя накатывать поверх новых записей.
После новых записей v95 исходный v94 нельзя снова допускать к записи, пока не
доказана сохранность новых полей и избранного его клиентом. SQL возврата сам
не переносит новые записи в старый снимок и не делает старый клиент безопасным.

Изолированные проверки сборщика:

```sh
python3 -m unittest discover -s tests -p test_family_release_bundle.py -v
```

Они используют только временный вымышленный checkout и локальный Git. Прохождение
этих проверок не подтверждает настоящий Safari, сохранность реальных очередей,
свежесть production-схемы или разрешение публикации.
