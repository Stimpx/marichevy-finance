# Продолжение семейного обновления на Windows · 29 октября 2026

Владелец сейчас без доступа к Mac и просит продолжить на Windows, затем выпустить
обновление: семейные записи давно приостановлены. Основной семейный выпуск уже
разрешён; повторного согласия на него не требуется. Доступность всех семи ранее
пронумерованных файлов на Windows ещё уточняется. Самостоятельный Windows verifier
собран; его настоящий запуск у владельца и сверка входов ещё не подтверждены.

Перенос сверки на Windows не меняет происхождение файлов: нужны серверный CSV
и отдельные ordinary/raw пары Mac, iPhone и Windows. Две копии Windows не заменяют

только при установленной проблеме с имеющимся файлом. Предыдущий Mac r3 остановился
с `verification-input-files` до запуска Node и чтения входов. Это не результат

### Нативный отказ запускателя и маленькая диагностика

29 октября владелец запустил распакованный комплект на Windows. До выбора файлов
получены `Result: failed` и `verification-launch-loader-failed`; стадии Node и
результата сверки нет. Причина пока не установлена. Этот код относится к внешнему
PowerShell loader и не подтверждает неисправность входных копий.

Точный исходный архив проверен: UTF-8 и SHA preflight совпадают с pin CMD, длина
команды допустима. На настоящем PowerShell 7.4.6 в Linux точный loader успешно
проверяет и вызывает исходный PS1; затем ожидаемо срабатывает внутренний Windows-
guard. Это не воспроизведение отказа Windows PowerShell 5 и не нативный pass.

Подготовлен [windows-verification-launcher-r2.zip](../preview/windows-verification-launcher-r2.zip):
2746 байт, внутри только `Start Windows verification.cmd`. SHA-256:
`72db04efff7d74d21a6f49c0d715b90c1d755127bb05d04ee0f121095cabee82`.
Скопировать этот один файл поверх прежнего CMD в распакованном комплекте.
Node, исходный PS1, manifest, bootstrap, приложение и все копии не заменяются.
Patch привязан к точному опубликованному архиву с SHA `d18b80b6…`; его builder
проверяет полные pins, а не произвольную папку или пользовательские файлы.

Новые фиксированные коды различают `folder`, `metadata`, `open`, `read`, `hash`,
`utf8`, `parse` и `invoke`. Ограниченный LanguageMode завершается до чтения файлов
с `verification-shell-restricted`; его ограничения не меняются и не обходятся.
Raw exceptions, пути и содержимое файлов не печатаются. Повторно создавать
резервные копии для этой диагностики не требуется. Устранение причины не заявлено.

Проверены 9 случаев настоящего PowerShell, 6 случаев patch-builder и 9 случаев
bundle/trust-chain. Выполнен также точный сгенерированный CMD loader с исходным
PS1: проверка pin и вход во внутренний guard прошли. Вымышленный constrained child
shell подтверждает безопасный отказ; политика ОС не менялась. Для дальнейшего
решения нужен новый фиксированный код с настоящего Windows.

### Ошибка row-lock в операторском скрипте исправлена

Владелец получил PostgreSQL42501 на `SELECT ... cron.job ... FOR UPDATE` до
вызова alter_job. Это не эффект кнопки Save: Save сохраняет текст, а показанная
ошибка относится к запуску SQL. Пауза не была выполнена; транзакция остановилась
до изменения задания. Первоначальная фикстура выполняла SELECT как владелец
таблицы и не воспроизводила ограниченные права managed postgres — этот пробел
проверки исправлен.

У обоих скриптов удалён прямой FOR UPDATE. Используется штатный alter_job:
upstream pg_cron временно переключает внутренний UPDATE на владельца расширения
и проверяет владельца задания. Публичный источник
https://raw.githubusercontent.com/citusdata/pg_cron/main/src/job_metadata.c
подтверждает устройство API, не конкретный production binary. Внутренний UPDATE
удерживает row lock; pre/post сравнение всей конфигурации сохраняется. Если другая
запись изменила её между первоначальным чтением и вызовом, postcheck вызывает
rollback. Прямые GRANT или смена роли владельца в production не выполнялись.
Начальный ROLLBACK завершает прежнюю неуспешную попытку, если её транзакция
осталась открытой.

Добавлены проверки с отдельной ролью без UPDATE: обычный SELECT разрешён,
FOR UPDATE и прямой UPDATE дают42501, а пауза/возврат через явно привилегированный
stand-in API сохраняют остальные поля и исходные ACL. Stand-in не является
native pg_cron. Фактический запуск исправления у владельца ещё ожидается.
Текущий targeted результат: 11/11 тестов, 16 исполнений офлайн PostgreSQL;
адаптация fixture-only database/current_user literals явно обозначена.

## Порядок до публикации

1. Установить, доступны ли на Windows все семь сохранённых файлов. Если часть
   осталась только на недоступном Mac, сохранить имеющиеся файлы и подготовить
   Windows-комплект, не объявляя закрытую сверку выполненной.
2. Проверить Windows launcher/IO/bundle и общий comparison/actual PostgreSQL WASM
   restore на вымышленных данных. Затем выполнить один настоящий owner-local
   запуск с семью исходниками. Передавать в чат только фиксированные result/codes.
   Тесты Linux не заменяют этот Windows native receipt.
3. Разобрать фактические различия, pending/conflicts, неизвестные поля, tombstones
   и связи. Сверка ничего автоматически не объединяет, не импортирует и не удаляет.
4. Подготовить операторский путь и короткое окно переключения. Исторический
   результат SQL Editor владельца `postgres` / `read_only=off` подтверждает
   возможный fallback без передачи ключа в чат; это **не текущая проверка роли,
   проекта или прав**. Перед выполнением проверить их заново, сохранить свежий
   частный резерв и сверить schema/grants/RLS/functions/triggers. Учесть все writers,
   а не только паузу ручного ввода.
5. При совпадении проверенного состояния применить точные 001 → 002 → 003, выполнить
   guarded activation согласованной семьи по проверенным параметрам и сохранить
   activation receipt. Не вставлять psql-шаблон с backslash-командами в SQL Editor;
   использовать отдельно проверенный совместимый операторский пакет.
6. После сервера опубликовать отдельный семейный static candidate, содержащий
   только разрешённые шесть файлов. Текущий кандидат —
   `53b5b428acf8b6f922796b191dcb9af456d0c68c`; diff против проверенного main
   меняет только `index.html`. Перед публикацией перепроверить основу и diff.
   Рабочую PR5 целиком не сливать.
7. Проверить выбранный Pages commit, HTTPS/CNAME и точный HTML SHA, вход и
   сохранность истории. Подтвердить разрешённую настоящую правку и server ACK
   на втором доступном устройстве, затем снять паузу. Недоступный Mac нельзя
   объявлять нативно проверенным; его старый writer не возобновлять до обновления.

Для выпуска остаются проверка настоящих данных и согласованное серверное
переключение. Наличие ZIP, совпадение итоговых сумм или прежний hosted pass сами
по себе эти действия не выполняют. Проверки и публикация продолжаются в рамках
уже данного разрешения владельца, без нового запроса согласия.
