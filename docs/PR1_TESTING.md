# Локальная проверка PR1

Локальный стенд запускается только на `127.0.0.1:8765`. Он отдаёт HTML и нужные иконки из этого репозитория, не показывает список файлов и не обслуживает методы изменения данных. Заголовок CSP запрещает соединения (`connect-src 'none'`), отправку форм, `<base>` и плагины. В ответе сервера значения `CONFIG` заменяются на отключённые; `index.html` на диске не меняется.

## Запуск

Из корня репозитория:

```sh
python3 tools/serve_staging.py
```

Откройте `http://127.0.0.1:8765/` в браузере на этой машине. Это локальная проверка; реальная авторизация не нужна и не должна использоваться. Не вводите реальные пароли, не включайте Telegram и не импортируйте семейный экспорт. Остановите сервер сочетанием `Ctrl+C`.

Чтобы проверить интерфейс без входа, запустите отдельный режим с пустым локальным набором:

```sh
python3 tools/serve_staging.py --fixture
```

Режим fixture использует отдельные ключи `marichevy_staging_*`, поэтому не читает и не меняет обычные ключи приложения даже на том же origin. Перед запуском приложения он удаляет только staging-ключ сессии; вход не нужен. Пустое состояние создаётся лишь если нет основного состояния, ожидающих изменений, блокировки восстановления и резервных или повреждённых копий. При повторной загрузке уже сохранённые staging-правки остаются. Для новой чистой проверки удалите данные сайта `127.0.0.1` в инструментах браузера.

## Проверка хранения и импорта

Используйте только вымышленные записи, созданные в staging или локально экспортированные из staging. Для проверки сохранения добавьте тестовую запись, перезагрузите страницу и убедитесь, что она осталась. Чтобы проверить повреждённое основное состояние в DevTools и не дать текущей вкладке сохранить поверх тестового значения при перезагрузке, выполните `localRecoveryBlocked = true; localStorage.setItem('marichevy_staging_state_v10', '{')`, затем перезагрузите страницу. Если есть корректная резервная копия или очередь, приложение восстановит данные; повреждённые исходные байты сохранятся в ключе с суффиксом `_corrupt_v1` при следующем сохранении. Если корректных копий нет, запись блокируется, повреждённые значения остаются без замены пустым состоянием.

Для проверки повреждённой резервной копии начните с чистого staging-хранилища, выполните `localRecoveryBlocked = true; localStorage.removeItem('marichevy_staging_state_v10'); localStorage.removeItem('marichevy_staging_pending_v10'); localStorage.setItem('marichevy_staging_state_backup_v44', '{')` и перезагрузите страницу: повреждённая копия должна остаться, новое пустое состояние не должно создаваться. После проверки удалите только тестовые данные сайта `127.0.0.1`.

Для проверки ошибки хранилища в консоли DevTools временно задайте `Storage.prototype.setItem = function () { throw new DOMException('test quota', 'QuotaExceededError'); }`, затем повторите локальное действие, которое сохраняет запись. Перезагрузка сбросит это изменение прототипа. Не используйте настоящий семейный JSON: проверяйте экспорт и импорт только файлом, созданным на этом же staging origin с вымышленными данными.

## Границы стенда

Это изолированный локальный просмотр на текущей машине. Он не является Cloudflare Preview, не проверяет реальную авторизацию, Supabase, Telegram, погоду или готовность backend. CSP блокирует сетевые запросы страницы. Формат данных приложения остаётся текущим; сервер не меняет отслеживаемый HTML и не мигрирует данные.
