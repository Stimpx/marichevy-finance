# Обратная связь: ошибки и предложения функций

Кандидат содержит два явных действия: «Сообщить об ошибке» и «Предложить функцию».
Они выбирают назначение обращения, сохраняя уже набранный текст и выбранный файл.
Получатель письма берётся из существующей константы `V88_FEEDBACK_SUPPORT_EMAIL`;
ввод пользователем не может заменить получателя. Тема и текст содержат тип,
выбранный раздел и идентификатор сборки из `v88FeedbackPayload().appVersion`.
Финансовые записи, localStorage, семья, профиль, сессия и технические логи в текст
или тело обращения автоматически не добавляются. Пользователь сам решает, какие
сведения написать и какой снимок приложить.

## Что фактически доступно

- «Написать на почту» составляет `mailto:` и передаёт его почтовому приложению.
  Это открытие черновика, а не подтверждение отправки или получения. Пользователь
  проверяет письмо, вручную добавляет снимок при необходимости и отправляет его.
- «Копировать», «Скачать .txt» и системное «Поделиться» сохраняют/передают введённый
  пользователем текст. Они не подтверждают доставку владельцу.
- Клиент содержит маршрут `CONFIG.url + /functions/v1/family-feedback`, однако
  реализации этой Edge Function, почтового сервиса и их развёртывания в текущем
  репозитории нет. Фактическое наличие удалённого маршрута этими изменениями не
  проверялось. Рабочие письма, таблицы и серверные настройки не менялись.

Наличие URL в HTML не устанавливает почтовую доставку. Отправка обоих типов на
почту без участия почтового приложения требует отдельной серверной реализации
и последующей проверки на изолированном стенде. Настоящие тестовые письма в рамках
этих изменений не отправлялись; сетевые проверки клиента полностью подменены.

## Конкретный контракт будущего серверного приёма

`POST /functions/v1/family-feedback` с `multipart/form-data`:

- `request_id`: UUID запроса; при повторе неизменённого обращения клиент сохраняет ID;
- `type`: `bug`, `idea`, `improvement` или `design`;
- `section`: один из известных клиентских разделов либо пустая строка;
- `message`: явный текст пользователя, 10–2500 значимых символов, без добавления истории;
- `appVersion`, `familyEdition`: сведения о сборке;
- `screenshot`: необязательный явный файл PNG/JPEG/WebP, до 5 МиБ.

Сервер должен самостоятельно проверить Auth JWT и действующее членство, не доверяя
идентификаторам семьи или адресу получателя из пользовательского тела. Не принимать
адрес доставки от клиента. Получателя задаёт защищённая серверная конфигурация,
согласованная с текущим адресом владельца. Токен сессии используется только в
защищённом заголовке запроса и не сохраняется в тексте/логах/почте.

Необходимы отдельное защищённое хранилище обращений, ограничение частоты/размера,
проверка действительного формата файла, идемпотентность по пользователю/семье/ID
и почтовая очередь с контролем повторов. Финансовая `family_state` не используется
как хранилище обратной связи. Запись обращения и постановка в почтовую очередь
должны быть согласованы, повтор с тем же ID возвращает прежнюю квитанцию.

Квитанция для нынешнего клиента:

```json
{
  "ok": true,
  "saved": true,
  "request_id": "тот же UUID запроса",
  "receipt_id": "непустой идентификатор сохранённого обращения",
  "emailNotified": true
}
```

`receipt_id` содержит 1–120 ASCII букв/цифр/`_.:-`, начиная с буквы или цифры.
`emailNotified` — настоящий JSON boolean. `true` допустим только после подтверждённого
принятия письма почтовым провайдером; это всё ещё не подтверждение попадания во
«Входящие». При сохранении без почтового ACK возвращается `false`, клиент сообщает
об отсутствии подтверждения почты и оставляет текст для альтернативной отправки.
Простой HTTP 200/`{"ok":true}`, чужой `request_id` или пропущенная квитанция не
показывают успех. При потерянном ответе клиент сообщает неизвестный результат,
сохраняет текст и ID для безопасного повтора, а не утверждает, что сервер ничего
не сохранил.

Выбор/подключение почтового провайдера и необходимые ему защищённые привязки —
следующий отдельный шаг после проверки доступной серверной инфраструктуры.
Ключи в HTML, чат или Git не добавляются; новые требования секретов этой доработкой
не создаются. Production DDL, развёртывание Edge Function и отправка реального
контрольного письма не выполняются автоматически. Приёмка почты требует отдельно
разрешённого адресного теста и подтверждения владельцем получения.

## Проверки кандидата

`tests/test_feedback_requests.py` использует только вымышленный текст, перехватывает
границу открытия почтового приложения и подменяет `fetch` ответами в памяти.
Внешняя сеть дополнительно блокируется браузерным harness. Проверяются оба
назначения, получатель из текущей конфигурации, метаданные и точное сохранение
текста, отсутствие финансовой истории в теле, честные статусы и квитанции/повторы.
Зелёный тест не означает, что письмо было отправлено или получено.
